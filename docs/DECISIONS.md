# 확정 결정 — Codex / Claude Code 공통

최종 정리: 2026-10-18 (KST) · 2026-10-26 D06 운영 활성화 확인 추가

현재 구현·검증·운영 상태는 [STATE](STATE.md), 작업 절차는 [AGENTS](../AGENTS.md)를 본다. 아래는 사용자 결정과 이를 반영한 구현의 기준이다. 단순 제안과 미결 과제는 마지막 절에 따로 둔다. 새 사용자 지시로 결정이 바뀌면 날짜·이유·대체되는 결정을 함께 갱신한다.

## D01. AI는 판단하고, 영양값은 조회하며, 계산·변경은 코드가 한다

- 근거: 초기 설계부터 유지한 역할 분리. [아키텍처](architecture.md), [chatPipeline](../src/application/chatPipeline.ts).
- Jev는 의도·대상·섭취 여부를 판단한다. 칼로리 합산·잔량·저장 변경을 모델의 생성 숫자에 맡기지 않는다.
- 음식의 영양값은 데이터셋에서 조회하거나 사용자가 직접 말한 kcal를 사용한다. 양의 추정은 D02에 따라 코드에서 처리하고 근거를 표시한다. 모르는 음식의 영양값을 새로 생성하는 것은 별개이며 허용된 것으로 해석하지 않는다.
- 목표는 조용한 오기록·누락 방지다. 평가셋의 0건 결과를 모든 실사용의 무오류 보장으로 표현하지 않는다.

## D02. 알려진 음식의 불확실한 양은 선기록 후보고한다

- 결정일: 2026-10-13. 사용자 피드백의 핵심은 g을 찾아 입력하게 하면 기록 자체를 포기한다는 점이었다. 구현 근거: `d2fda77`, `67a33f5`.
- 먹은 것으로 판단된 알려진 음식은 양·단위가 불확실하다는 이유만으로 g 질문부터 하지 않는다. 합리적인 양으로 추정 기록하고 `~`, 적용 기준, 쉬운 정정 방법을 알린다.
- `assumed`는 앱의 추정 기준이며 공식 출처가 있는 값처럼 표시하지 않는다. 음식별 분량·대표 기준과 앱 추정값을 구분한다. [servingReferences](../src/ai/nutrition/servingReferences.ts), [영양 타입](../src/ai/nutrition/types.ts) 참조.
- 10월 13일 확장: 조금/약간/살짝은 기본 0.5회분, 많이는 1.5회분. 입·젓가락·점·가닥·국자를 지원한다. 밥은 양이 있을 때 쌀밥, 샐러드는 채소 샐러드로 대표 해석하고 이를 알린다. 재료 표현 처리는 알려진 단일 요리를 전제로 한다.
- **질문을 모두 없앤 결정은 아니다.** 섭취 여부 불명확, 미지원 음식, 수정 대상·남긴 양 불명확, 여러 기록을 건드리는 수정 등에는 확인이 남는다. 현재 띄어쓰기 나열의 확인도 유지된다. add의 양 추정 정책을 modify/delete에 임의로 확대하지 않는다.
- 이 결정은 과거 문서의 "양을 모르면 g을 묻는다"를 알려진 음식의 추가 기록 범위에서 대체한다.

## D03. 반복 보고는 기본적으로 추가 섭취다

- 근거: 2026-10-07 `86cd255`.
- 같은 음식을 다시 입력한 것을 단순 중복으로 제거하지 않는다. 수정 의도와 추가 섭취 의도를 구분한다. 추가와 수정 양쪽 모두 기록이 조용히 누락되지 않게 검증한다.

## D04. 로그인 없이 기존 사용 경험을 유지한다

- 사용자 결정일: 2026-10-07. [계정 준비 지시서의 D1~D5](CODEX-HANDOFF-2026-10-07-account-prep.md#1-사용자가-확정한-결정-2026-10-07).
- 로그인은 선택이다. 기존 익명 localStorage 저장 형태를 유지한다. 대화·동기화 메타데이터는 별도 키에 둔다.
- 로그인한 계정으로 기기 기록을 합칠 수 있어야 한다. 실제 전송은 명시적 합치기 동의를 받은 뒤 처리하고, 확인 전 로컬 원본을 삭제하지 않는다.
- 합치기의 현재 구현은 [accountMerge](../src/application/accountMerge.ts)와 운영 메모를 확인한다. 초기 계획서의 스키마 제안을 구현된 스키마로 오인하지 않는다.

## D05. 대화는 KST 기준 30일, 신체 프로필은 별도 동의

- 사용자 결정일: 2026-10-07. 대화는 오늘과 이전 29개 날짜를 보관한다. 식사·목표는 대화 보관 기한으로 지우지 않는다.
- 계산기 신체정보는 기본적으로 이 기기에만 둔다. 서버 보관을 켜려면 별도 동의가 필요하다. 철회·재동의 경계를 지키고, 판단 API와 기록 합치기에 신체정보가 섞이지 않게 한다.
- 프라이버시 약속을 바꿀 때는 화면 안내와 해당 경계를 검증하는 테스트를 함께 바꾼다. [privacy.test.ts](../src/privacy.test.ts), [계정 운영 메모](account-operations-2026-10-07.md) 참조.

## D06. 구현과 계정 기능 공개·운영 활성화를 구분한다

- 근거: 2026-10-07 계정 운영 기록. 계정 코드는 기능 스위치 뒤에 두며, 실제 제공자 검증과 공개 조건을 확인하기 전 공개 완료로 보고하지 않는다.
- 카카오 연결 해제는 후속 사용자 요청에 따라 즉시 삭제안에서 **7일 복구 유예** 방향으로 코드를 준비했다. 사용자가 직접 선택하는 계정 삭제는 즉시 처리하는 경로다.
- 유예 보관 근거 확인과 운영 적용은 별도다. 기존 승인이나 코드 완료를 migration·웹훅·기능 스위치 활성화 승인으로 재사용하지 않는다. 상세 상태와 순서는 [운영 메모](account-operations-2026-10-07.md#카카오-연결-해제-코드-준비-운영-미적용)를 따른다.
- 요청·Jev 사용량 제한을 둔다. 현재 메모리 카운터의 제한을 인정하고, 계정 공개 확대 전에 공유 카운터 등 비용 통제 조건을 확인한다.
- **2026-10-26 사용자 확인: 운영의 `ACCOUNT_ENABLED=on`은 의도한 것이며 유지한다.** 같은 날 재조회에서 production이 `on`이고 `/api/account`가 `configured: true`였다. 이로써 선택 로그인(google·kakao)은 운영에서 열린 기능이다. 계정 운영 메모의 "공개 전 확인을 마치기 전 `on`으로 바꾸지 않는다"는 이 범위에서 대체된다.
- 이 확인은 `ACCOUNT_ENABLED`에만 해당한다. `ACCOUNT_RECOVERY_ENABLED`, 카카오 해제 migration·Edge Function·웹훅의 운영 적용은 여전히 별도 승인 대상이다. 남은 확인(Google 실제 로그인, 개인정보처리방침 항목, 백업, 공유 요청 제한)은 없어지지 않고 운영 중 해결할 과제가 된다. 이를 "확인 완료"로 보고하지 않는다.

## D07. 핵심 경험은 텍스트 기록과 쉬운 정정이다

- [원래 피드백 요구사항](product/user-feedback-requirements.md)과 10월 13일 D02를 함께 적용한다. 사진이나 복잡한 입력 폼 없이 음식 입력·기록 확인·정정을 마칠 수 있어야 한다.
- 답장은 음식·양·kcal·추정 기준을 알아볼 수 있게 하되 과한 격려·훈계·건강 코칭을 추가하지 않는다.
- 초기 문서의 "스트릭은 넣지 않는다"는 현재 범위가 아니다. `f4c19b9` 이후 개인 기록 스트릭이 구현됐다. 월간 챌린지의 실제 참여·순위 서비스는 아직 준비 단계이며 확정 출시로 확대 해석하지 않는다.
- 새 데이터·브랜드를 늘릴 때 실제 입력 실패 사례와 제품·용량의 정확한 연결을 기준으로 한다. 식품 수 자체가 성공 지표는 아니다.

## D08. 작업 범위·승인·인수인계는 저장소에서 공유한다

- 근거: 기존 단계별 작업 방식, 최근 범위 내 완료까지 진행하라는 사용자 지시, 2026-10-18 공통 문서 정비 요청.
- 전체 방향을 설명하고 승인된 작업 단위를 순서대로 마무리한다. 이미 승인된 구현·검증을 매번 재승인받지 않는다. 요청하지 않은 다음 단계나 운영 변경으로 확대하지 않는다.
- 커밋·push는 해당 작업의 사용자 승인을 따른다. `main` push는 Git 연동으로 production 배포를 유발한다. 도구별 과거 세션 승인을 새 작업에 이월하지 않는다.
- 사용자 환경 파일과 기존 미커밋 변경을 보존한다. 한 checkout의 동시 수정을 피하고, 병렬 구현이 필요하면 별도 branch/worktree를 사용한다.
- 결정·상태를 개인 메모에만 두지 않는다. 작업 종료나 도구 전환 전에 STATE를 갱신하고, 원칙 변경은 이 파일에 반영한다. 대화 전체나 비밀값을 옮길 필요는 없다.

## 아직 확정하지 않은 것

- Claude Code를 영구 주 도구로 고정하는 결정. 현재 제안은 주 작업 도구 하나와 다른 도구의 검토를 조합하되 작업 경계에서 넘기는 방식이다.
- 다음 구현 기능·일정, 추정값의 실사용 적합성 개선 범위, 스트릭·챌린지 확대의 우선순위.
- 카카오 해제·복구 기능의 운영 적용 시점. 계정 기능 자체의 운영 활성화는 2026-10-26 D06에서 확인됐다.
- 공급자 조건의 미확인 사항, 운영 백업·복구 방식, 인스턴스 간 공유 요청 제한의 구체 구현. 기존 코드가 이 결정을 대신하지 않는다.
