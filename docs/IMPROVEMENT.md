## 1. 자가 발전 루프 — 실패 한 건마다

수집 → 분류 → 회귀 사례화 → 수정 → 측정 → 기록 → 배포 판단 → 재검증 안내

### 1-1. 수집

- [ ] 실패한 **입력 문장**, 기대 결과, 실제 결과, 날짜, 기준 커밋을 남긴다. 대화 원문 전체나 신원 정보는 공통 문서에 옮기지 않는다.
- [ ] 출처를 적는다: 테스터 피드백 / 본인 실사용 / 배포 smoke / 사용자가 직접 정정한 기록.

### 1-2. 분류 — 하나를 고른다

| 분류 | 판단 기준 | 우선순위 |
| --- | --- | --- |
| 조용한 오기록 | 다른 음식·양·kcal로 저장됐는데 알리지 않음 | 최우선 |
| 조용한 누락 | 먹은 음식이 기록에서 빠짐(예: 과거 `라면 김밥 두 줄`) | 최우선 |
| 불필요한 질문 | 알려진 음식인데 양 때문에 g을 물음(D02 위반) | 높음 |
| 정정 실패 | 수정·삭제 대상을 잘못 잡거나 되돌릴 수 없음 | 높음 |
| 추정 부적합 | 기본량이 실제 먹는 양과 크게 다름 | 중간 |
| 미지원 음식·제품 | 데이터에 없음. 제품·용량을 정확히 연결할 수 있을 때만 추가(D07) | 중간 |
| 의도 판단 오류 | 먹지 않은 것을 기록하거나 먹은 것을 거름(Jev 판단) | 사례별 |
| 표시·문구 | 기록은 맞지만 답장·목록에서 이해하기 어려움 | 낮음 |

### 1-3. 회귀 사례로 만든다

- [ ] 일반 입력은 [평가 입력](../fixtures/food-input-coverage.json), 수식어는 `fixtures/food-modifier-cases.json`·`food-modifier-boundary-cases.json`에 추가한다.
- [ ] 고치기 전에 그 사례가 실제로 실패하는지 먼저 확인한다.
- [ ] 기존 기대값을 바꿀 때(예: 10월 13일 밥·샐러드 4건) 이유를 커밋 메시지에, 원칙이 바뀌면 DECISIONS에 남긴다.

### 1-4. 고친다

- [ ] 모델이 만든 숫자로 합산·저장하지 않는다(D01).
- [ ] 양 추정 정책을 modify/delete로 넓히지 않는다(D02).
- [ ] 데이터는 식약처 행을 근거로 한다. 포장제품은 칸 방식(사람은 "한 개 = 어느 칸"만 정함), 묶음 행 사용 금지, 일상 단어와 겹치면 `brand: true`([10월 6일 기록 §5](product/user-feedback-status-2026-10-06.md#5-대표-포장제품-10개-칸-방식-2026-10-06)).
- [ ] 저장 형태를 바꾸면 기존 익명 localStorage 키와 호환을 확인한다(D04). 프라이버시 경계를 바꾸면 화면 안내와 `privacy.test.ts`를 함께 바꾼다(D05).

### 1-5. 측정

- [ ] `pnpm typecheck` · `pnpm lint` · `pnpm test` · `pnpm build`
- [ ] `pnpm eval:food-coverage`: [기준선](../fixtures/food-input-coverage.baseline.json) 대비 silent wrong/drop 0/0, 이전에 맞던 사례의 퇴보 0, 새 사례 통과
- [ ] 수식어를 건드렸으면 `pnpm eval:food-modifiers`
- [ ] 판단 경로를 건드렸으면 `pnpm eval:food-judgment`. Jev 실호출·과금이 생기므로 실행 전에 사용자에게 확인한다.
- [ ] 날짜·KST 경계를 건드렸으면 날짜 테스트, 화면을 건드렸으면 3000이 아닌 포트에서 브라우저 확인
- [ ] 실행하지 않은 검증은 이유와 함께 "미실행"으로 적는다.

### 1-6. 기록한다

- [ ] STATE: 기준 HEAD, 변경, 직접 실행한 검증과 수치, 미실행 이유, 남은 문제, 다음 행동
- [ ] 원칙이 바뀌면 DECISIONS에 날짜·이유·대체되는 결정
- [ ] 이 문서 §3의 해당 할 일 상태
- [ ] 다른 프로젝트에도 쓸 만한 지식이면 Wiki에 `hw propose`(status: proposed)로 제안한다. 확정은 소유자만 한다.

### 1-7. 배포를 판단한다

- [ ] 커밋·push는 이 작업에 대한 사용자 승인을 받는다. `main` push는 문서만 바뀌어도 production 배포다.
- [ ] push 전에 되돌릴 배포를 Vercel에서 다시 확인한다. 과거 문서의 배포 ID를 그대로 쓰지 않는다.
- [ ] 배포 후 smoke: 이번에 고친 문장 + 추가·정정·삭제·되돌리기 기본 흐름. 결과를 STATE에 적는다.

### 1-8. 재검증을 안내한다(R15)

- [ ] 고친 항목 목록과 다시 해볼 예시 문장을 준비한다. 테스터에게 보내는 것은 사용자가 따로 지시할 때만 한다.
