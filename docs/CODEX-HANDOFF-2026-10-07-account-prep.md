## 2. 절대 원칙 (기존 그대로)

- **AI는 판단하고, 칼로리는 조회하고, 계산은 코드가 한다.** Jev는 의도와 대상만 판단한다. 칼로리 숫자는 MFDS 행, 출처 있는 1인분 기준, 사용자가 말한 숫자에서만 나온다. 대화 기록에 저장하는 숫자도 이미 기록된 값이나 답장 문구에 이미 있는 숫자뿐이다.
- **조용히 틀리는 것 0, 조용히 빠지는 것 0.** 저장이 실패하면 실패했다고 말한다. 기록이 소리 없이 사라지면 안 된다.
- 답장 문구는 `replyText.ts`·`historyText.ts`에서 코드로 만든다. 짧게 사실만 쓰고, 칭찬·경고·건강 판정은 하지 않는다.
- 이 프로젝트의 베타 요소는 Jev 하나다. **1·2단계에서는 의존성을 추가하지 않는다.** `privacy.test.ts`가 의존성 목록을 고정하고 있다. 꼭 필요하다고 판단되면 추가하지 말고 멈춰서 보고한다.

## 3. 1단계: 이 기기 안의 대화 기록과 동기화용 데이터 모양

### 3-1. 저장 모양: 기존 키는 그대로 두고 새 키를 추가한다

**바꾸면 안 되는 것:** `hmcl.v1.mealRecords`, `hmcl.v1.dailyGoals`, `hmcl.v1.dietProfile`, `hmcl.v1.onboarding`의 envelope과 각 항목 스키마(`src/infrastructure/schemas.ts`)는 그대로 둔다.

이유는 이렇다. `mealRecordSchema`·`dailyGoalSchema`는 `z.object`라서 모르는 필드를 **떼어 버린다.** 기존 레코드에 `deletedAt`을 넣었다고 하자. 이전 배포로 롤백하면, 그 빌드는 삭제 표시를 모른 채 지운 기록을 다시 보여 준다. 쓰는 순간 표시도 사라진다. 새 키에 두면 이전 빌드는 그 키를 무시할 뿐이고, 기존 동작은 그대로다.

**새 키** (`storage.ts`의 `STORAGE_KEYS`에 추가하고, 이름은 제안이다):

```
hmcl.v1.conversation   { version: 1, turns: ConversationTurn[] }
hmcl.v1.syncMeta       { version: 1, removedRecords: { id, removedAt }[], goalSetAt: { [date]: ISO } }
```

- **`removedRecords`(삭제 표시):** `MealRecordRepository.remove(id)`가 기록을 지울 때 id와 시각을 남긴다. 기록은 지금처럼 `mealRecords`에서 실제로 지운다. 그래서 `getByDate`·`getAll`의 결과는 바뀌지 않는다.
  - 되돌리기로 같은 id가 다시 `add`되면 표시를 지운다. 지금 `restoreFoodItem`이 같은 id로 되살리는지, 새 id를 만드는지 먼저 확인하고 보고한다.
  - 음식 항목 하나만 지우는 경우는 레코드 `update`(items 변경)로 처리된다. 이것은 `updatedAt`으로 합칠 수 있으므로 표시가 필요 없다.
  - 표시는 자동으로 지우지 않는다. 크기가 작고, 나중에 계정에 합칠 때 필요하다.
- **`goalSetAt`:** `DailyGoalRepository.set(goal)`이 그 날짜의 목표를 정한 시각을 남긴다. 키가 없는 날짜는 "시각 모름"이다. 이전 데이터가 모두 이 상태이고, 정상이다.
- 기존 저장소의 공개 동작과 포트 시그니처(`domain/repository.ts`)는 바꾸지 않는다. 메타데이터를 읽는 길은 따로 작은 포트로 만든다. 지금은 테스트와 이후 단계만 쓴다.
- **쓰기 순서:** 기록 쓰기가 성공한 뒤에 메타를 쓴다. 메타 쓰기가 실패해도 기록은 남는다. 이 경우 나중에 합칠 때 정보가 부족해지는 것뿐이다. 반대 순서는 쓰지 않는다.

### 3-2. 대화 기록 `ConversationTurn`

```ts
type ConversationTurn = {
  id: string;              // crypto.randomUUID()
  at: string;              // ISO, offset 포함
  user: string | null;     // 사용자가 입력한 문장 또는 고른 선택지의 표시 문구. × 탭처럼 말이 없으면 null
  reply: string;           // 화면에 보인 앱 답장 텍스트 그대로
  outcome: "added" | "modified" | "removed" | "restored" | "asked" | "cancelled"
         | "nothing_added" | "answered" | "failed";
  recordIds: string[];     // 이 턴이 만들거나 바꾸거나 지운 MealRecord id
};
```

- **한 턴의 단위:** 사용자의 입력 하나(문장이나 선택지 탭)와 그 결과로 화면에 보인 답장 하나. 질문 → 선택 → 기록처럼 여러 턴에 걸친 흐름은 턴 여러 개로 남는다.
- 답장 문구는 `Reply`를 화면에 그리는 쪽과 **같은 함수**에서 텍스트를 얻는다. 저장용 문구를 따로 만들지 않는다.
- **저장하지 않는 것:** Jev 원본 응답, confidence, 요청 본문, 프로필 값.
- 목록의 × 삭제와 그 되돌리기도 턴으로 남긴다(`user: null`). 무엇이 사라졌는지 나중에 따라갈 수 있어야 하기 때문이다. 넣지 않는 쪽이 낫다고 판단되면 이유와 함께 보고한다.
- 대화 기록 저장소도 포트와 localStorage 구현으로 나눈다. 기존 저장소들과 같은 방식이다. 깨진 JSON이나 모르는 version은 빈 기록으로 읽는다. 항목 하나가 깨지면 그 항목만 버린다(`parseValidEntries`).

**30일 보관 (D4)**
- 하루의 경계는 `domain/date.ts`의 KST 기준이다. 오늘과 그 전 29일, 즉 **30개 날짜**의 턴만 남긴다. 날짜 단위로 자르면 히스토리에서 하루치 대화가 중간에 잘려 보이지 않는다. 다르게 해석해야 할 이유가 보이면 보고한다.
- 정리는 앱이 대화 기록을 읽을 때와 쓸 때 한다. 시계는 주입해서 테스트한다.
- **식사 기록과 목표는 30일 정리 대상이 아니다.** 대화만 정리한다.
- localStorage 용량이 차서 쓰기에 실패하면 오래된 턴부터 지우고 다시 쓴다. 그래도 실패하면 대화 기록만 포기한다. **식사 기록 저장은 대화 기록 저장의 성공 여부와 상관없이 진행된다.**

### 3-3. 화면 (R07)

- `/history`에서 날짜를 열면 그날의 대화를 시간순으로 보여 준다. 각 턴에서 그 턴이 만든 기록(음식, 양, kcal)을 볼 수 있다. 피드백 원문은 "무엇을 먹고 9kcal였는지 알 수 없다"였다. 이 문제가 풀렸는지가 기준이다.
- 기록의 `sourceText`(이미 저장되어 있다)를 히스토리의 음식 기록 쪽에서도 볼 수 있게 한다. 피드백 상태 문서 R07의 남은 문제다.
- 30일보다 오래된 날짜는 식사 기록만 보이고, "대화는 30일까지 보관해요" 같은 짧은 안내를 붙인다. 문구는 `historyText.ts`에서 만든다.
- 오늘 화면의 말풍선 UI(한 번의 주고받기)는 바꾸지 않는다. 대화 전체 보기는 히스토리에서만 한다. 오늘 화면에도 넣는 게 낫다고 판단되면 구현하지 말고 제안만 한다.
- 화면 문구에 "서버", "동기화", "로그인"을 쓰지 않는다. 아직 없는 기능이다.

### 3-4. 1단계 검증

- 단위 테스트
  - 새 저장소들(깨진 값, 모르는 version, 30일 경계: TZ=UTC·LA에서도 KST 기준, 용량 초과 시 오래된 것부터)

## 4. 2단계: 사용량 제한 (R14)

배경: `/api/chat`·`/api/resolve`에는 요청 제한이 없다. `/api/chat`은 요청마다 Jev를 호출하고, Jev 호출은 과금된다. 로그인과 가입을 열기 전에 막아야 한다.

### 4-1. 만들 것

- **요청 제한 포트** `RateLimiter`와 **메모리 구현**을 만든다. 키, 창(window), 한도를 받아 허용·거절과 `retryAfter`를 돌려준다. 시계는 주입한다.
- **키:** 클라이언트 IP(Vercel이 주는 헤더. 어떤 헤더를 믿을지 Next 16 문서와 Vercel 문서로 확인하고, 근거를 보고에 적는다)를 **서버 비밀값으로 HMAC한 값**으로 쓴다. 원본 IP는 저장하거나 로그에 남기지 않는다. 비밀값이 없을 때(로컬)의 동작을 정하고 테스트한다.
- **두 단계 한도:**
  1. IP별 분당 한도와 일간 한도. `/api/chat`과 `/api/resolve`를 따로 센다. `/api/resolve`는 Jev를 거치지 않으므로 한도를 더 넉넉하게 잡는다.
  2. **Jev 일간 총 호출 상한**(전체 사용자 합계, KST 하루). 상한에 닿으면 Jev를 호출하지 않는다.
- **넘었을 때:** `429`(요청 제한)와 `Retry-After`를 돌려준다. Jev 상한이라면 지금의 `judgment_unavailable` 503과 구분되는 에러 코드를 쓴다. 클라이언트는 "요청이 많아요. 잠시 후 다시 해 주세요" 같은 짧은 안내를 보여 준다. 문구는 `replyText.ts`에서 만든다. **아무것도 저장하지 않는다.**
- **mock으로 바꾸지 않는다.** 한도를 넘었다고 `mockJudge`로 판단하면 사용자 모르게 판단 품질이 떨어진다. 조용히 틀리는 경로가 된다. (키가 없을 때 mock으로 동작하는 지금의 개발용 동작은 그대로 둔다.)
- **한도 숫자:** `env.ts`에 선택 변수로 추가하고 기본값을 둔다. 기본값은 **잠정치**로 표시하고, 근거를 주석과 보고에 적는다. 근거는 실제 사용 패턴(한 끼 기록에 오가는 요청 수), Jev rate limit(문서상 1,200 req/min) 같은 것이다. **`.env.local`·`.env.example`은 사용자가 직접 관리한다. 고치지 말고, 추가한 변수 목록을 보고에 적는다.**

### 4-2. 이 단계의 한계: 반드시 보고에 적는다

Vercel 서버리스 함수는 인스턴스끼리 메모리를 공유하지 않는다. 그래서 메모리 구현은 **인스턴스별 최선 노력**일 뿐이고, 전체 한도나 Jev 일간 상한을 정확히 지키지 못한다. 공유 저장소(KV/Redis 계열, Vercel 방화벽의 rate limit 규칙, 나중에 정할 DB)는 **아직 정하지 않은 스택과 묶인 결정**이다.

- 포트만 맞추면 공유 저장소 구현으로 바꿀 수 있게 만든다.
- 공유 저장소 후보를 2~3개 조사한다. 의존성 추가 여부, 무료 범위, Vercel과의 연결 방식을 정리하되, **구현하지 말고** 보고에 표로 적는다.
- Jev와 TypeSafe 쪽에서 쓸 수 있는 예산 알림이나 상한 기능이 있는지 `https://docs.typesafe.ai/llms.txt`에서 확인해 같이 적는다.

### 4-3. 2단계 검증

- 단위 테스트
  - 창 경계, 한도 직전·직후, `Retry-After` 값
  - 키 HMAC(원본 IP가 결과나 로그에 없는지)
  - Jev 상한(상한에서는 judge가 호출되지 않는지를 spy로 확인)
  - KST 날짜가 바뀔 때 카운터 초기화
- route 테스트: 429 응답일 때 본문 모양, 기존 400·503 응답이 그대로인지
- 클라이언트: 429나 상한 응답을 받았을 때 안내가 뜨고, 아무것도 기록되지 않으며, 대기 중이던 질문 상태가 깨지지 않는지
- **실제 과금을 일으키는 부하 테스트는 하지 않는다.** 실제 Jev 키로 반복 호출하지 않는다. 로컬에서 한도를 1~2로 낮추고 브라우저로 확인한다(Jev 키 없이 mock 상태여도 된다. 이 단계의 검증 대상은 Jev가 아니라 제한이다).
- `privacy.test.ts` 통과(의존성 변화 없음), `pnpm typecheck` · `lint` · `test` · `build`

**2단계가 끝나면 멈추고 보고한다.**

## 5. 작업 환경 규칙

- **커밋과 push는 사용자가 승인할 때만 한다.** `main`에 push하면 곧바로 Vercel production에 배포된다(https://how-much-calories-left.vercel.app). 단계를 마치면 커밋 단위와 메시지를 **제안만** 한다. 커밋 메시지는 영어로 `type: summary` 형식을 쓰고, 본문에 "왜"를 적는다. `git log`를 참고한다. 커밋마다 단독으로 typecheck·lint·test가 통과하게 나눈다.
- Windows + pnpm 환경이다. 사용자가 3000번 포트에 자기 `next dev`를 띄워 두는 경우가 많다. **그 프로세스를 죽이지 않는다.** 브라우저 확인은 `pnpm build && pnpm start --port 3200`처럼 다른 포트에서 한다. 다른 포트는 다른 origin이라 localStorage가 비어 있고, 사용자의 실제 기록을 건드리지 않는다. 확인이 끝나면 띄운 서버를 정리한다.
- 사용자의 실제 localStorage(3000번 origin과 production)를 읽거나 바꾸지 않는다.
- Git Bash의 `curl -d '<한글>'`은 CP949로 보낸다. 한글 본문은 UTF-8 파일로 만들어 `--data-binary @file`로 보낸다.
- `pnpm sync:mfds`는 이번 작업과 관계없다. 돌리지 않는다(약 29분, 데이터셋 파일을 다시 쓴다).
- 답장과 보고는 한국어로 쓴다. 막힌 것과 불확실한 것은 정리된 척하지 말고 그대로 적는다.
