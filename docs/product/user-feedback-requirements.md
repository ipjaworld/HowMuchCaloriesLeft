# 사용자 피드백 기반 요구사항 및 Claude Code 작업 컨텍스트

- 작성일: 2026-10-06
- 대상: HowMuchCaloriesLeft
- 근거: 사용자가 제공한 개인 피드백 대화와 2026-09-26~2026-10-06 오픈채팅 텍스트
- 문서 상태: 요구사항 분석 및 우선순위 제안. 현재 코드의 구현 여부는 미확인.
- 개인정보 처리: 이름, 소속 세부 정보, 제품과 무관한 사적 대화는 제외했다.

## 1. 이 문서를 읽는 에이전트에게

이 문서는 사용자 경험에서 도출한 요구사항이다. 모든 항목을 현재 발생 중인 버그나 확정된 구현 지시로 간주하지 않는다. 피드백 이후 이미 개선된 항목이 있을 수 있다.

먼저 다음 순서로 작업한다.

1. 저장소의 AGENTS.md와 작업 대상 경로에 적용되는 지침을 읽는다.
2. 현재 구현을 조사해 각 요구사항을 `구현됨 / 부분 구현 / 미구현 / 확인 필요`로 분류한다.
3. 관련 코드 위치, 판단 근거, 검증 결과를 제시한다. 문서나 주석만으로 동작을 확정하지 않는다.
4. P0부터 해결 순서와 변경 범위, 필요한 검증을 제안한다.
5. 초기 인계 단계에서는 코드 수정 없이 분석 결과를 제시한다. 이후 사용자가 구현을 요청하면 승인된 범위에서 진행한다.

Next.js 관련 코드를 변경하기 전에는 AGENTS.md에 따라 설치된 `node_modules/next/dist/docs/`의 관련 가이드를 읽는다. 이 문서는 특정 모델, 데이터베이스, 인증 서비스 또는 아키텍처를 강제하지 않는다.

## 2. 제품의 핵심 가치

> 사진 없이, 대충 말해도 음식과 양을 알아듣고, 믿을 만하게 계산해주며, 나중에 기록을 다시 볼 수 있다.

주요 사용 상황은 다음과 같다.

- 엄격한 식단 관리보다는 일상적으로 섭취 칼로리를 확인하고 싶다.
- 제품 검색이나 상세 폼 작성 대신 친구에게 말하듯 기록하고 싶다.
- 카메라를 사용할 수 없는 환경에서도 식단 기록을 끝내고 싶다.
- 같은 음식을 반복해서 먹으며 매번 기록하는 부담을 느낀다.

위 내용은 소수 피드백에서 확인한 상황이다. 전체 시장이나 특정 집단의 수요가 검증된 것으로 확대 해석하지 않는다.

## 3. 근거와 우선순위 해석

### 근거 구분

- **사용자 관찰·요구:** 실제 사용 중 불편, 선호, 재사용 의사.
- **개발자 설명·계획:** 당시 구현 설명, 기술적 고민, 향후 계획. 현재 상태와 다를 수 있다.
- **개선 가설:** 피드백을 해결하기 위해 이 문서에서 제안한 방법. 구현 방식과 효과는 검증이 필요하다.

### 우선순위 제안

- **P0:** 음식 기록의 정확성·완결성·신뢰를 훼손하는 문제.
- **P1:** 기록 확인, 정정, 입력 편의 등 다음 사용성 개선.
- **P2:** 계정·동기화·커뮤니티 등 수요와 효과를 추가 검증할 확장.
- **확대 배포 전:** 운영 비용과 과도한 사용에 대한 통제.

일정과 공수는 산정하지 않았다. 우선순위는 현재 구현 조사 후 조정할 수 있다.

## 6. 중요한 판단 원칙

### 적게 묻기와 정확성의 균형

`질문을 절대 하지 않는다`는 목표를 채택하지 않는다. 피드백에는 입력 부담과 잘못된 결과로 인한 불신이 모두 존재한다.

- 음식·양·대상이 명확하면 바로 처리한다.
- 합리적인 기본량으로 진행할 수 있다면 적용한 양과 추정임을 표시한다.
- 중요한 정보가 빠져 결과가 크게 달라지면 최소한의 질문을 한다.
- 수정·삭제 대상이 여러 개면 임의로 선택하지 않는다.
- 인식하지 못해도 이유와 다음 행동을 안내해 사용자가 막히지 않게 한다.

구체적인 확인 질문 기준과 기본량은 현재 데이터·구현을 조사한 뒤 정한다.

### 결과를 검증할 수 있어야 함

결과에는 적어도 인식한 음식, 섭취량, 칼로리, 추정 여부를 연결해 보여준다. 세부 영양 데이터 출처와 계산 기준을 확인하는 방식은 구현 단계에서 결정한다.

400kcal, 9kcal, 찌개 300kcal 미만 등의 숫자만으로 오류라고 확정하지 않는다. 음식 종류와 실제 섭취량, 제공량 기준을 확인해야 한다. 제공된 텍스트에는 `사진` 표기만 있으며 실제 캡처 내용은 확인하지 못했다.

### 음식 개수보다 실제 입력 성공

음식을 약 122개에서 450개까지 늘린다는 말은 당시 개발자 목표다. 현재 데이터 수나 달성 여부는 미확인이다. 음식 개수 증가만으로 R03~R06이 해결됐다고 판단하지 않는다.

핵심 성공 기준은 사용자가 별도 검색이나 불필요한 재입력 없이 기록을 마칠 수 있는지다. 사용자 원문을 기반으로 누락과 오인식 사례를 확인한다.

## 7. 완료 기준 및 검증 예시

아래는 기대 동작이다. 실제 통과 여부는 아직 검사하지 않았다. 칼로리 정답은 확인된 제품·영양 데이터와 섭취량을 기준으로 설정한다.

| 연결 ID | 입력 또는 행동 | 기대 결과 |
| --- | --- | --- |
| R01 | 같은 제품에 `햇반 1/2`, `햇반 0.5개`, `햇반 반 개` 입력 | 같은 기준 제품·단위에서 동일한 섭취량과 칼로리. `1/2`를 2개로 처리하지 않음. |
| R02 | `햇반 1/2 + 제육 + 김치` | 세 음식으로 분리. 반 개는 햇반에만 적용. 제육·김치에 적용한 양 또는 필요한 확인을 표시. |
| R03 | 지원하는 브랜드·제품명과 `한 봉지` 입력 | 해당 제품으로 매칭하고 해당 포장량 기준으로 계산. |
| R03, R06 | 미지원 브랜드·제품명 입력 | 다른 제품으로 조용히 확정하지 않음. 미지원 상태와 추가 정보 또는 추정 경로 안내. |
| R03 | `소금빵 먹었어` | 지원 데이터가 있으면 연결. 양이 없으면 적용 기준을 표시하거나 필요한 질문으로 진행. |
| R04, R06 | `케이크 먹었어` | 추정 기준을 보여주거나 필요한 질문으로 진행 가능. 수많은 후보를 그대로 나열하거나 임의의 특정 제품을 확정하지 않음. |
| R05 | 확인된 제품의 100g당 데이터와 실제 섭취량으로 계산 | 기준량 환산이 올바르고 화면의 음식·양·계산 결과가 일치. |
| R05 | 의심스러운 칼로리 결과 상세 확인 | 매칭 음식, 적용한 양, 기준량을 추적할 수 있음. 숫자만 보고 오류를 판정하지 않음. |
| R07 | 기록 후 앱을 닫고 같은 브라우저·저장 환경에서 다시 열기 | 저장 정책 범위에서 이전 입력과 해석·계산 결과를 다시 확인 가능. |
| R08 | 수정 대상이 명확한 상황에서 `2개 아니고 1개야` | 기존 기록만 수정되고 합계 갱신. 새 음식 중복 추가 없음. |
| R08 | 후보가 여러 개인 상황에서 `아까 먹은 바나나 1개 뺄게` | 필요한 대상을 확인한 후 수량 감소 또는 삭제 적용. 의도치 않은 다른 기록 변경 없음. |
| R08 | 수정·삭제 후 되돌리기 | 변경 전 기록과 합계로 복원. |
| R09 | 초기 키·몸무게 입력 화면 사용 | 키·몸무게 순서와 단위가 명확하고 잘못된 입력을 확인·수정할 수 있음. |
| R10 | 카메라 사용 없이 입력·추가 설명·정정 수행 | 전체 기록 흐름 완료 가능. |
| R14 | 설정한 요청·비용 한도 초과 상황 | 설계한 제한이 적용되고 사용자 안내와 운영 측 확인이 가능. 실제 과금을 발생시키는 부하 테스트 없이 검증 방식을 먼저 정함. |

현재 검증 환경에 맞는 테스트를 선택한다. 문서 내용만 반복하는 형식적 테스트보다 실제 수량 파싱, 매칭, 기록 저장·수정 동작을 확인한다.

## 8. 추천 작업 순서

1. **현황 조사:** R01~R15의 구현 상태와 근거를 작성한다.
2. **핵심 입력과 계산:** R01~R06을 중심으로 사용자 사례를 재현하고 수정한다.
3. **기록과 정정:** R07~R10을 점검하고 기존의 좋은 정정 경험을 보존한다.
4. **반복 사용:** R11의 입력 부담 감소 효과를 검증한다.
5. **확장 검증:** R12~R13의 수요와 도입 시점을 판단한다.

R14는 확대 배포 전에 별도로 충족해야 한다. R15는 각 개선 배포 이후 재검증에 활용한다. 이는 개발 일정이나 모든 작업의 엄격한 선후관계를 확정한 것이 아니다.

## 9. 현황 조사 결과 작성 형식

Claude Code는 최초 분석 결과를 다음 형식으로 정리하면 된다.

| ID | 구현 상태 | 관련 코드 위치 | 판단·검증 근거 | 남은 문제 | 제안 변경 범위 |
| --- | --- | --- | --- | --- | --- |
| R01~R15 각각 | 구현됨 / 부분 구현 / 미구현 / 확인 필요 | 파일 및 관련 함수·컴포넌트 | 확인한 동작 또는 미확인 사유 | 구체적인 차이 | 영향 범위와 검증 방법 |

추가로 현재 구현에서 이미 해결된 사항, P0 권장 작업 순서, 의사결정이 필요한 미확정 사항을 짧게 설명한다.

## 10. 이번 문서로 확정하지 않는 것

- 특정 AI 모델 교체 또는 추가 도입.
- 사진 인식 기능의 우선 개발.
- 군인 등 특정 집단에 대한 제품 방향 확정.
- 로그인·커뮤니티·랭킹을 즉시 구현해야 한다는 결론.
- 실제 캡처가 없는 숫자 사례의 오류 확정.
- 현재 코드 수정, 배포, 외부 사용자에게 메시지 전송.

이 문서의 목적은 사용자 피드백을 코드 조사와 구현 계획으로 연결할 공통 컨텍스트를 제공하는 것이다.
