### ② 반복 사용

- 같은 음식을 다시 말하면 추가 섭취로 기록된다(D03). 최근·자주 먹은 음식 다시 넣기, `어제랑 똑같이` 같은 기능은 없다. 날짜 표현은 현재 범위 밖이다(coverage `unsupported_date`).
- 앱은 사용 데이터를 서버로 모으지 않는다. "기록 부담" 측정(T20)은 별도 장치 없이는 사용자 인터뷰나 본인 사용 기록에 의존한다.
- 어떤 형태(목록 버튼 / 대화 명령 / 둘 다)로 할지는 제품 결정이다(D07: 텍스트 기록과 쉬운 정정이 핵심).

### ③ 입력 품질과 LLM

- 오프라인 coverage(Jev 미사용) 85.9%, Jev guard 가정 89.2%, silent 0/0. 남은 실패의 대부분은 `spurious_ask` 19건: 이야기 속 음식 아닌 구절("운동했어", "헬스장 가기 전")이 미지원 음식 질문이 된다. 운영에는 Jev 후보 필터(8A)가 있어 일부를 거른다.
- 실사용 실패 문장을 모으는 경로가 없다(T10). 개선 판단의 근거(Wiki `D-20261025-stop-token-optimization`: 실제 사용의 누락·오답)가 부족하다.
- LLM 후보: (a) Jev `choice`로 미지원 구절을 데이터셋 후보에 연결 — 새 제공자 없음. (b) 생성형 LLM 추출기 — 새 제공자·국외 이전 고지·비용·지연 발생. 어느 쪽이든 D01(숫자는 조회·코드) 안에서 "구절 추출·후보 선택"만 맡긴다. 로컬 LLM은 2026-09-30 측정에서 Jev에 졌다.
- 실제 Jev 평가(`eval:food-judgment`)는 191회 호출로 과금된다.

## Phase 계획

### 영역 A — 운영 중인 계정 기능의 위험

**A1. 턴 단위 원자 저장 (T35) — 자동 진행**
- 서버: `batch` 변경 종류 추가. 여러 변경을 같은 `mutateAccountData`로 순서대로 적용하고 revision을 한 번만 올린다. 하나라도 실패하면 아무것도 저장하지 않는다. `import`는 batch에 넣지 않는다.
- 클라이언트: 계정 저장소에 턴 시작·커밋을 추가한다. 턴 동안의 변경은 캐시에 적용하고(읽기는 바뀐 값을 본다) 모아 둔다. 턴 끝에 대화 기록까지 한 번에 저장한다. 실패하면 캐시를 버리고 다시 읽고 "저장되지 않았다"고 알린다. 로그인하지 않은 로컬 저장은 바꾸지 않는다.
- 검증: 서버·저장소 단위 테스트(전부 저장/전부 미저장, revision 충돌, 크기 초과), typecheck·lint·test·build, coverage 불변, 격리 포트 브라우저에서 비로그인 흐름 회귀 확인. 로그인 상태 실제 확인은 계정 로그인이 필요해 하지 않는다.
- 끝나면: 검증이 통과하면 A2로 넘어간다.

**A2. 계정 운영 결정 묶음 — 완료 후 확인 요청**
- 개인정보처리방침 보완 초안을 `/privacy`에 반영한다(배포 안 함). 국외 이전 항목 정리, 안전성 확보조치, 쿠키·브라우저 저장, 권익침해 구제 안내.
- 결정 메모: T34 공유 카운터 저장소 선택지(지연·비용·장애 시 동작), T33 백업 선택지, T31 적용 조건, T30 Google 로그인 점검 절차(사용자 수행).
- 끝나면: **멈추고 확인 요청.** 법적 사실과 선택은 사용자 몫이다.

**A3. (A2 결정 후) T34 공유 카운터 구현** — 선택한 저장소의 `RateLimiter` 구현, 저장소 장애 시 동작, 격리 테스트. 운영 적용(migration·env)은 별도 승인.

**A4. (A2 결정 후) 백업·카카오 유예 운영 적용** — 사용자 승인 범위만.

### 영역 B — 반복 사용

**B1. 반복 기록 설계안 — 완료 후 확인 요청**
- 후보: ⓐ 오늘 화면에 최근·자주 먹은 음식 버튼(탭하면 같은 양으로 기록, 정정 가능) ⓑ 대화 명령 `어제 점심이랑 똑같이`, `아까 그거 하나 더` ⓒ 둘 다. 기록 부담 측정 방법(T20) 포함.
- 끝나면: **멈추고 확인 요청.** UX 형태가 제품 결정이다.

**B2. 선택한 방식 구현과 검증** — 저장 형태 불변(D04), 반복은 추가 섭취(D03), 기록 후 정정 경로 유지.

### 영역 C — 입력 품질

**C0. 대화를 받아 주는 답장 — 완료(2026-10-26, 문구 사용자 확인, 로컬 커밋).** 사용자 지시로 C1보다 먼저 했다. 생성형 LLM 없이, Jev가 기록이 아니라고 판단한 문장에만 데이터 기반 답장을 붙인다(D07 갱신). 생성형 LLM은 실제 대화 기록을 모은 뒤 이 방식으로 안 되는 입력이 얼마나 되는지 보고 판단한다.

**C1. 실패 사례 수집 경로 (T10) — 설계 후 확인 요청**
- 후보: 사용자가 대화 내역에서 "이 답이 틀렸어요"를 눌러 문장만 내보내기(서버 전송 없음) / 본인 사용 기록 주기적 검토. 개인정보 경계(D05)에 영향.

**C2. 기준선 측정** — 실패 사례 + 기존 corpus로 Jev 실호출 평가. 과금 승인 필요.

**C3. LLM 도입 판단** — (a) Jev 후보 매핑 (b) 생성형 추출기를 같은 실패 사례셋으로 비교. 채택 기준: silent wrong/drop 0 유지, 불필요한 질문 감소, 지연·비용. 새 제공자를 쓰면 A2의 개인정보처리방침에 반영해야 한다.

**C4. 채택안 구현** — 기본 off 스위치 뒤에 두고 측정 후 켠다.
