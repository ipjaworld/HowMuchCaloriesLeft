## 1. 요약

1. **로그인부터 만들지 않는다.** 먼저 대화 기록(R07)을 **이 기기 안에서** 남긴다. 요구사항 문서에도 "대화 기록이 로그인을 기다릴 필요는 없다"고 적혀 있다. 이때 만드는 데이터 모양이 나중에 서버로 그대로 올라간다.
2. **로그인을 열기 전에 사용량 제한(R14)을 먼저 건다.** 지금 `/api/chat`에는 요청 제한이 없다. 가입을 열면 사용자가 늘고, Jev 과금도 같이 늘어난다.
3. **로그인은 선택 기능으로 둔다.** 지금처럼 로그인 없이 바로 쓸 수 있어야 한다. 로그인하면 기록을 백업하고 여러 기기에서 볼 수 있다.
4. **신체 정보(키·몸무게·나이·성별)는 처음에는 이 기기에만 둔다.** 화면에 적힌 "이 기기에만 저장되며 서버에 전송되지 않습니다" 약속과 `privacy.test.ts`가 지키는 범위를 이것으로 유지할 수 있다. 서버에 올리는 것은 식사 기록, 목표 숫자, 대화 기록이다.
5. **인증·DB에는 이미 많이 쓰이는 관리형 서비스를 쓴다.** 이 프로젝트의 실험 요소는 Jev 하나뿐이다("베타 요소는 하나"). 인증·DB는 직접 만들지 않는다.

### 동기화를 넣을 때 막히는 데이터 모양 세 가지

1. **삭제를 기억하지 않는다.** 지금 `remove()`는 기록을 실제로 지운다. 두 기기를 합칠 때 "A에서 지운 기록"과 "B에만 있는 기록"을 구분할 수 없어서, 지운 기록이 다시 살아난다. 삭제 표시(`deletedAt`)가 필요하다.
2. **`DailyGoal`에 시각이 없다.** `{ date, calorieTarget }`뿐이다. 두 기기에서 같은 날 다른 목표를 정하면 어느 쪽이 나중에 정한 것인지 알 수 없다. 앱의 규칙인 "마지막에 정한 것이 이긴다"를 지키려면 `setAt`이 필요하다.
3. **대화 기록이라는 개념이 없다.** R07을 하려면 새로 만들어야 한다.

세 가지 모두 **로그인 없이도 먼저 고칠 수 있다.** 그래서 1단계에 넣었다.

## 3. 원칙

기존 원칙에서 이어지는 것과, 이번에 새로 제안하는 것이 섞여 있다. 새로 제안하는 것은 (제안)이라고 표시했다.

- **AI는 판단만 하고, 계산은 코드가 한다.** 저장소를 바꿔도 이 경계는 그대로다. 서버 DB에도 칼로리는 기록된 값 그대로만 들어간다.
- **조용히 틀리는 것 0, 조용히 빠지는 것 0.** 동기화에도 같은 기준을 둔다. 기기를 합치다가 기록이 소리 없이 사라지거나 중복되면, 음식을 잘못 기록한 것과 같은 실패다. (제안)
- **로그인 없이 쓰는 경로를 없애지 않는다.** 처음 써 보는 사람이 가입부터 해야 하면 안 된다. (제안)
- **약속을 바꿀 때는 화면 문구와 테스트를 같은 커밋에서 바꾼다.** `privacy.test.ts`는 지우지 않고, 새 약속에 맞게 고친다. (제안)
- **이미 검증된 버전만 쓴다.** 정식 버전이 아니거나 베타인 인증 라이브러리는 쓰지 않는다.

## 4. 단계

지금까지처럼 단계마다 멈추고 보고한다. 단계마다 typecheck·lint·test·build를 돌린다. 커밋과 push는 단계마다 따로 승인받는다.

### 1단계 — 이 기기 안의 대화 기록과 동기화용 데이터 모양 (R07, 로그인 없음)

- 대화 기록 `ConversationTurn`을 새로 만든다. 저장 키는 `hmcl.v1.conversation`이다.
  - 필드: `id`, `at`, 사용자 문장, 앱 답장 텍스트, 결과 종류(기록함 / 고침 / 지움 / 물어봄 / 취소 / 정보 없음), 이 턴이 만들거나 바꾼 `recordIds`
  - Jev 원본 응답과 confidence는 저장하지 않는다. 화면에 필요 없고, 보관하는 데이터만 늘어난다.
- 히스토리 화면에서 날짜별 대화와 그 대화로 생긴 기록을 함께 보여 준다. "무엇을 먹고 9kcal였는지"를 따라갈 수 있게 한다. `sourceText`도 화면에 보인다.
- `MealRecord`에 `deletedAt`을 추가하고, `DailyGoal`에 `setAt`을 추가한다. 둘 다 선택 필드로 두고, 예전 기록은 그대로 읽는다. 화면에서 하는 동작은 바뀌지 않는다.
- 보관 기간은 사용자가 정한다(§6). 정할 때까지는 무기한으로 둔다. localStorage 용량이 차면 오래된 대화부터 지우고, 식사 기록은 지우지 않는다.
- 검증: 대화와 기록 연결, 되돌리기 후 대화 표시, 저장소가 깨졌을 때 빈 상태로 읽기, 용량 초과.
- **얻는 것:** 로그인 없이도 R07이 해결된다. 2·4단계는 이 데이터 모양을 그대로 쓴다.

### 2단계 — 사용량 제한 (R14, 가입을 열기 전에 필요)

- `/api/chat`·`/api/resolve`에 요청 제한을 건다. 처음에는 IP 기준으로 두고, 3단계 이후 계정 기준을 추가한다.
- Jev 호출 수 집계와 예산 상한을 둔다. 상한을 넘으면 "잠시 후 다시" 안내를 보여 주고, mock 판단으로 바꾸지 않는다. 다른 판단기로 몰래 바꾸면 조용히 틀릴 수 있다.
- 제한 상태를 저장할 곳이 필요하다. 3단계의 DB나 Vercel의 KV 계열 저장소를 쓴다. **이 저장소를 무엇으로 할지가 3단계 스택 결정과 묶여 있다.** 스택을 먼저 정하면 같은 서비스를 쓸 수 있다.
- 검증: 실제 과금을 일으키는 부하 테스트는 하지 않는다. 시계와 카운터를 주입한 단위 테스트, 로컬에서 한도를 낮춘 브라우저 확인으로 대신한다.

### 3단계 — 로그인만 (데이터 동기화 없음)

- 가입, 로그인, 로그아웃, 계정 삭제를 만든다. 로그인해도 데이터는 여전히 이 기기에만 저장된다. 이 단계만 배포해도 아무것도 사라지지 않는다.
- Next 16에서는 middleware가 **`proxy.ts`로 이름이 바뀌었다.** 공식 가이드는 proxy에서 쿠키만 보고 확인하라고 한다. 실제 권한 확인은 데이터에 가까운 곳(DAL, 즉 route handler와 server action)에서 하라고 권한다(`authentication.md` §Optimistic checks with Proxy, §Data Access Layer). 이 앱에서 보호할 것은 API뿐이고 페이지는 공개다. 그래서 proxy 없이 route 안에서만 확인하는 구성이 가능한지 먼저 본다.
- 개인정보처리방침 페이지와 가입 동의 화면(필수 항목, 만 14세 이상 확인)을 만든다. 화면의 프라이버시 문구도 "로그인하지 않으면 이 기기에만…"으로 바꾼다.
- `privacy.test.ts`: 의존성 목록 고정을 새 목록으로 갱신한다. "프로필 모듈은 어떤 route에서도 닿지 않는다"는 검사는 **그대로 유지한다.**

### 4단계 — 서버 저장소 (로그인한 사용자만)

- `MealRecordRepository`·`DailyGoalRepository`·대화 저장소의 서버 구현을 만든다. 화면은 로그인 여부에 따라 저장소를 고른다. 도메인과 application 계층은 바뀌지 않는다. 포트가 처음부터 이것을 위해 `async`였다.
- 로그인한 사용자의 정본은 서버에 둔다. localStorage는 읽기 캐시로만 쓴다. 오프라인에서 쓰기는 지원하지 않는다. 연결이 끊기면 "저장하지 못했어요"라고 보여 주고 아무것도 저장하지 않는다. 이렇게 하면 오프라인 큐와 충돌 해결이 필요 없다.
- 소유권은 DB 정책(행 단위 접근 제어)과 DAL에서 **두 번** 확인한다.
- 하루 경계는 `domain/date.ts`의 KST 고정을 서버도 그대로 쓴다. 이미 순수 함수다.
- `/api/chat`의 요청 형태는 이 단계에서 바꾸지 않는다. 클라이언트가 오늘 항목을 보내는 방식을 유지한다. 서버가 직접 읽는 방식은 측정할 이유가 생기면 그때 바꾼다.

### 5단계 — 이 기기의 기록을 계정으로 옮기기

- 처음 로그인할 때 한 번 묻는다. "이 기기의 기록 N개와 목표를 계정으로 옮길까요?" 묻지 않고 옮기지 않는다.
- 합치는 규칙(코드가 결정한다):
  - 기록은 `id`로 합집합을 만든다. 같은 id가 있으면 `updatedAt`이 늦은 쪽을 쓴다. 삭제는 `deletedAt`으로 반영한다.
  - 목표는 날짜마다 `setAt`이 늦은 쪽을 쓴다. `setAt`이 없는 예전 목표는 서버 값보다 우선하지 않는다.
  - 대화는 `id`로 합집합을 만든다.
- 옮긴 뒤 결과를 숫자로 보여 준다(기록 ○개, 목표 ○개). 로컬 원본은 이전이 확인될 때까지 지우지 않는다.
- 검증: 두 기기에서 같은 계정으로 옮기기, 한쪽에서 지운 기록, 같은 날 다른 목표, 중간에 실패, 두 번 옮기기(아무것도 늘지 않아야 한다).

### 6단계 — 신체 프로필 동기화 (선택, 별도 동의)

- §6의 결정 4번에 따라 할지 말지 정한다. 한다면 기본은 꺼 두고, 사용자가 켤 때 별도로 동의받는다. 서버에 저장하는 값은 계산기 입력값뿐이다. 유지 칼로리는 지금처럼 저장하지 않고 계산한다.
- 하지 않으면 다른 기기에서는 계산기를 다시 입력한다(30초). 목표 숫자는 4단계에서 이미 동기화되므로, 매일 쓰는 데는 지장이 없다.

### 7단계 — 운영과 테스터 공개 (R15)

- 내 데이터 내보내기(JSON)와 계정 삭제 시 즉시 파기를 만든다. 백업 보존 기간도 개인정보처리방침에 적는다.
- 기존 테스터에게 보낼 안내 초안을 만든다. 실제 발송은 따로 지시받았을 때 한다.

## 5. 스택 후보

**아래 버전 상태와 요금은 이 보고서에서 확인하지 않았다.** 결정하기 전에 0단계로 공식 문서를 읽고 확인한다. Next 16 공식 가이드가 예로 드는 것은 Better Auth, Clerk, NextAuth.js(Auth.js), Supabase이고, 세션 라이브러리로는 iron-session과 jose다.

| 후보 | 장점 | 걸리는 점 |
|---|---|---|
| **Supabase** (Auth + Postgres + 행 단위 보안) — **추천** | 인증, DB, 행 단위 접근 제어가 한 서비스에 있다. 카카오·구글 로그인 제공자가 있다. 2단계 제한 카운터도 같은 DB에 둘 수 있다 | 의존성이 하나 늘어난다. 무료 플랜의 비활성 일시정지 정책과 서울 리전 가능 여부를 확인해야 한다 |
| Better Auth + Postgres(Neon 등) + ORM | 인증 테이블을 직접 소유한다. 공급자에 덜 묶인다 | 직접 짜는 코드와 의존성이 가장 많다. ORM도 새로 고르고 검증해야 한다 |
| Clerk + 별도 DB | 로그인 UI와 계정 관리가 완성돼 있다 | 사용자 정보가 외부 서비스에 하나 더 있다. 데이터는 결국 별도 DB가 필요하다 |
| Auth.js(NextAuth) v5 | 익숙하고 자료가 많다 | v5가 오래 베타였다. 아직 베타라면 "베타 요소는 하나" 원칙에 걸린다 |

**로그인 방식:** 카카오 + 구글 소셜 로그인을 추천한다. 비밀번호를 받지 않으면 비밀번호 저장, 재설정 메일, 유출 대응을 만들 필요가 없다. 카카오는 이메일을 받으려면 비즈 앱 전환이 필요할 수 있다. 개인 개발자 앱으로 어디까지 되는지 확인해야 한다. 이메일 없이 카카오 회원번호만으로 계정을 만드는 방법도 있다.

## 6. 결정 (2026-10-07 사용자)

- 로그인하지 않으면 지금 기능과 지금 스키마 그대로 쓸 수 있다. 그래서 1단계의 새 정보는 기존 키가 아니라 **새 localStorage 키**에 둔다.
- 로그인하면 이 기기의 데이터를 그 계정에 합친다(5단계).
- 프로필을 서버에 저장하려면 사용자 동의 모달이나 절차가 필요하다(6단계).
- 대화 보관 기간은 일단 30일.
- 1·2단계를 먼저 한다. 작업 지시: [`docs/CODEX-HANDOFF-2026-10-07-account-prep.md`](../CODEX-HANDOFF-2026-10-07-account-prep.md)
- 아직 정하지 않은 것: 로그인 방식, 스택(아래 2·3번)

## 6-1. 처음 정리한 결정 항목

1. **로그인을 필수로 할지, 선택으로 할지.** 추천은 선택이다. 로그인하지 않으면 지금과 똑같이 동작한다.
2. **로그인 방식.** 카카오만 / 카카오 + 구글 / 이메일 매직링크 / 이메일 + 비밀번호. 추천은 카카오 + 구글이다.
3. **스택.** 추천은 Supabase다. 정하시면 0단계로 버전·요금·리전·카카오 조건을 확인하고 보고한다.
4. **신체 프로필을 서버에 둘지.** 추천은 처음에는 이 기기에만 두는 것이다. 키·몸무게처럼 건강과 이어지는 정보는 개인정보보호법상 민감정보에 해당하는지, 동의를 별도로 받아야 하는지 판단해야 한다. **저는 법률 자문을 드릴 수 없다.** 올리기로 하면 그 전에 확인이 필요하다. 식사 기록 자체도 같은 질문에서 완전히 자유롭지 않다. 개인정보처리방침을 쓸 때 함께 확인하는 것을 권한다.
5. **대화 기록 보관 기간.** 무기한 / 90일 / 30일. 그리고 로그인 후 서버에 대화 기록도 올릴지 정해야 한다.
6. **순서.** 위 1→2단계(로그인 전 작업)를 먼저 할지, 로그인을 먼저 볼지 정해야 한다. 요구사항 문서는 R12를 "실제 수요 확인 후"로 적었다. 여러 기기를 쓰는 테스터가 실제로 있었는지 짧게 확인해 두면, 4~6단계의 범위를 줄일지 판단하는 근거가 된다.
