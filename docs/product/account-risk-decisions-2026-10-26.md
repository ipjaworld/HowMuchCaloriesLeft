[실행 계획](execution-plan-2026-10-26.md)의 Phase A2 결과다. 계정 기능은 운영에서 켜져 있다(D06, 2026-10-26 사용자 확인). 아래는 사용자가 정해야 하는 것과 그 근거다. 표시: `[사실]` 코드·설정에서 확인 · `[추정]` 측정하지 않은 값 · `[확인 필요]` 계약·법률 확인 대상.

## 1. 개인정보처리방침 보완 초안 — 검토 요청

`src/app/privacy/page.tsx`를 고쳤다(**미커밋·미배포**). 근거: 개인정보 보호법 제28조의8 제2항(국외 이전 고지 항목)과 시행령 제31조(처리방침 기재 항목).

바뀐 것:
- 9개 절로 재구성: 처리 목적·항목 / 보유·파기 / 위탁·국외 이전 / 안전성 확보 조치 / 쿠키·브라우저 저장 / 내 정보 관리 / 보호책임자 / 권익침해 구제 / 변경.
- 국외 이전을 수령자별로 정리했다: 이전 국가, 위탁 업무, 이전 항목, 시기·방법, 보유 기간, 거부 방법·효과, 연락처.
  - TypeSafe에 보내는 항목은 코드 기준이다 `[사실]`: 입력 문장, 판단 시각, 목표 숫자, 최근 음식 기록(이름·양·kcal·시각), 판단할 문장 조각.
  - Vercel 함수 리전 `iad1`(미국 동부) `[사실]`.
  - 계정 기능이 꺼진 환경에서는 Supabase 항목을 숨긴다.
- 안전성 확보 조치는 코드에 있는 것만 적었다 `[사실]`: HTTPS, RLS 본인 행 제한, HttpOnly 쿠키, HMAC 카운터, 관리자 키 미사용, 분석 도구 없음(`privacy.test.ts`가 검사).
- 기존 문구(로그인 없이·계정·계산기·보관·카카오 복구 조건부 절)는 내용을 유지하고 위치만 옮겼다.

확인이 필요한 것:
1. **국외 이전 근거** `[확인 필요]`: 초안은 "서비스 제공에 필요한 위탁·보관 + 처리방침 공개"(제28조의8 제1항 제3호 가목)로 썼다. 이용약관이 없고 비로그인 사용자도 TypeSafe로 문장이 가므로, 이 근거로 충분한지 아니면 별도 동의가 필요한지 판단이 필요하다.
2. **Supabase 국외 처리 국가와 연락처** `[확인 필요]`: 저장 리전은 서울이다. 운영·지원 처리 국가와 개인정보 문의처는 DPA에서 확인하지 못해 링크만 넣었다.
3. **Google·카카오**: 이용자가 직접 인증하는 제공자로 보고 위탁 표에 넣지 않았다. 이 해석이 맞는지 확인이 필요하다.
4. **민감정보 해당 여부** `[확인 필요]`: 식사 기록·키·몸무게가 건강 관련 민감정보로 해석될 여지가 있는지.
5. **시행일**: 초안 값은 `2026년 10월 26일`이다. 게시하는 날로 바꾼다(`EFFECTIVE_DATE`).
6. 보호책임자를 운영자 본인으로 적었다. 권익침해 구제 기관 연락처는 일반 표준 안내다.

## 2. T34 공유 요청 제한 — 저장소 선택

현재: 인스턴스별 메모리 카운터 `[사실]`. Fluid compute라 한 인스턴스가 많은 요청을 받지만, 인스턴스·배포 사이에 공유되지 않는다. Jev 하루 2,000회 상한은 인스턴스마다 따로 적용된다.

| 안 | 장점 | 단점 |
| --- | --- | --- |
| ⓐ Supabase RPC(원자적 카운터 함수) | 새 제공자 없음. 비용 없음 | 함수(미국 동부)↔DB(서울) 왕복이 요청마다 추가된다(약 0.2초 `[추정]`). 공개 키로도 RPC를 부를 수 있어, 전역 Jev 예산 소진을 막으려면 서버 전용 비밀 인자와 DB 설정이 필요하다. DB가 멈추면 제한도 멈춘다 |
| ⓑ Upstash Redis(Vercel Marketplace, 미국 동부 리전) | 함수와 같은 지역이라 지연이 작다. 원자적 증가가 기본 기능이다 | 새 제공자와 계정(사용자가 생성)이 필요하다. 처리방침에 수탁자를 추가해야 한다(저장값은 HMAC 키와 횟수) |
| ⓒ 현 상태 유지 + 공개 규모 제한 | 작업 없음 | 비용 상한이 보장되지 않는다. 테스터 안내 발송(T36) 전까지만 유효하다 |

- 공통 설계 `[제안]`: 공유 저장소가 실패하면 지금의 메모리 제한으로 대신한다. 저장소 장애가 앱 장애가 되지 않게 한다.
- 권장: **ⓑ**. 지연과 남용 방지 설계가 단순하다. 새 제공자를 피하고 싶으면 ⓐ.
- 결정 후 Phase A3에서 `RateLimiter` 구현, 장애 시 대체 동작, 격리 테스트를 만든다. 운영 연결(키·env·migration)은 별도 승인이다.

## 4. T31 카카오 연결 해제 — 지금 상태의 위험

- 운영에는 해제 웹훅이 없다 `[사실: migration·Edge Function·웹훅 미적용, recovery off]`. 이용자가 카카오 설정에서 앱 연결을 끊으면 **앱은 알 수 없고, 계정 기록이 DB에 계속 남는다.** 이용자가 앱에서 직접 계정을 삭제하는 경로는 동작한다.
- 적용 순서(준비 완료): ① 7일 유예 보관의 근거 확인 ② migration 적용 ③ Edge Function 배포 ④ 카카오 콘솔 웹훅 등록 ⑤ `ACCOUNT_RECOVERY_ENABLED=on`. ②~⑤는 운영 변경이라 사용자 승인이 필요하다.
- 결정 필요: 유예 정책으로 적용 / 즉시 삭제로 되돌림 / 보류.

## 5. T30 Google 실제 로그인 — 사용자 점검 절차

실제 계정 로그인은 사용자가 직접 해야 한다.

1. Google Cloud Console → OAuth 동의 화면의 **게시 상태** 확인. "테스트"이면 등록된 테스트 사용자만 로그인할 수 있다. 운영에서 기능이 켜져 있으므로, 이 상태면 일반 이용자에게 로그인 실패가 보인다.
2. 시크릿 창에서 `/account` → Google 로그인 → 동의·연령 확인 → 콜백 후 로그인 상태 표시.
3. 음식 하나를 기록 → 새로고침 → 그대로 있는지 확인. 다른 브라우저에서 같은 계정으로 보이는지 확인.
4. 로그아웃 → 다시 로그인 → 기록 유지 확인.
5. (선택) 테스트 계정이면 계정 삭제 → 기록이 사라지는지 확인.
6. 결과를 [계정 운영 메모](../account-operations-2026-10-07.md)에 날짜와 함께 기록한다.

이 점검은 Phase A1의 턴 단위 저장(배포 후)도 함께 확인한다. 로그인 상태에서 음식을 기록하면 요청 한 번(`batch`)으로 저장돼야 한다.
