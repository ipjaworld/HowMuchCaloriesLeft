# 오늘 얼마 먹어도 돼?

먹은 걸 평소 말하듯 입력하면 기록하고, **오늘 앞으로 얼마나 더 먹을 수 있는지** 바로 보여주는 앱.

> **MVP v0.1** — 자연어로 기록·수정·삭제가 실제로 동작합니다. 아래 대화는 실제 출력입니다.

```
나: 갈비탕 하나 먹었어
앱: 기록했어요. 오늘 362 kcal 먹었어요. 1,738 kcal 남았어요.

나: 밥 한 공기 먹었어
앱: 어떤 밥인가요?   [쌀밥] [현미밥]
나: (쌀밥)
앱: 기록했어요. 오늘 713 kcal 먹었어요. 1,387 kcal 남았어요.

나: 아까 갈비탕 반만 먹었어
앱: 갈비탕을 고쳤어요. 오늘 532 kcal 먹었어요. 1,568 kcal 남았어요.
```

## 핵심 UX

화면은 셋뿐이다. **오늘 상태 · 오늘 먹은 것 · 대화 입력창.**

커뮤니티, 배지, 스트릭, 체중 그래프, 운동 프로그램, 물 섭취 기록은 넣지 않는다. 사용자가 CRUD 폼을 직접 조작하는 대신 자연어로 말하면 앱이 의도를 판단해 기록을 바꾼다. 판단이 애매하면 멋대로 바꾸지 않고 **짧게 되묻는다.**

말투도 짧게 유지한다. 과한 격려나 건강 코칭을 하지 않는다.

```bash

pnpm build

pnpm eval:jev                  # 실제 Jev로 골든셋 60건 측정 (TYPESAFE_API_KEY 필요)
EVAL_JUDGE=mock pnpm eval:jev  # 규칙 기반 fallback 기준선 (키 불필요)
```

`eval:jev`와 `sync:mfds`는 개발용이다. `pnpm test`는 네트워크를 전혀 타지 않는다.

pnpm이 없다면 corepack으로 켠다.

```bash
corepack enable --install-directory ~/.local/bin pnpm
```

## 환경변수

`.env.example`을 `.env.local`로 복사해서 쓴다. 실제 키는 절대 커밋하지 않는다.

변수는 **런타임에 필요한 것**과 **로컬 데이터 동기화에만 쓰는 것**으로 나뉜다. 아래는 코드의 실제 사용처를 추적해서 정리한 것이다.

### 런타임 (배포 시 설정)

| 변수 | 필수 | 사용처 |
| --- | --- | --- |
| `TYPESAFE_API_KEY` | **아니오** | `src/app/api/chat/route.ts` — Jev 판단. **없으면 결정론적 mock 판단으로 앱 전체가 정상 동작한다.** 없는 상태는 지원되는 상태지 고장이 아니다 |

**런타임에 필요한 건 이것 하나뿐이다.** 앱은 커밋된 `data/korean-foods.json`을 읽으므로 실행 중 외부 영양 API를 호출하지 않는다.

### 로컬 데이터 동기화 전용 (배포에 불필요)

| 변수 | 사용처 |
| --- | --- |
| `MFDS_FOOD_NUTRITION_API_KEY` | `scripts/syncMfdsDataset.sync.ts`에서만. 데이터셋을 다시 만들 때만 필요 |
| `MFDS_FOOD_NUTRITION_ENDPOINT` | 같은 스크립트. 기본값이 있어 보통 건드릴 일 없다 |

### 아직 쓰이지 않음

| 변수 | 상태 |
| --- | --- |
| `ANTHROPIC_API_KEY` | 스키마에만 있고 **호출하는 코드가 없다.** LLM fallback 파서를 넣을 때를 위한 자리 |

전부 서버 전용이다. `src/env.ts`는 클라이언트에서 import되면 예외를 던지고, `NEXT_PUBLIC_*` 변수는 하나도 없다.

식약처 키는 [data.go.kr 15127578](https://www.data.go.kr/data/15127578/openapi.do)에서 활용신청하면 개발계정은 자동승인된다.

## Jev가 하는 일 / 하지 않는 일

Jev는 ChatGPT 같은 생성형 챗봇의 대체재가 아니다. **문장을 만들지 않고, 타입이 정해진 판단과 확률을 돌려준다.**

**하는 일**

- intent 판단 — `add_food` / `modify_food` / `delete_food` / `ask_status` / `ask_recommendation` / `other`
- 지금 말한 게 실제로 먹은 것인지 (`갈비탕 칼로리 높아?`를 기록으로 저장하면 안 된다)
- 기록을 바꾸기 전에 사용자 확인이 필요한지
- 최근 기록 중 무엇을 가리키는지 (`아까 밥`이 어느 항목인지)

**하지 않는 일**

- 산술 (`2100 - 1580`은 TypeScript가 한다)
- 칼로리 합산
- 음식의 칼로리 값 생성 — 영양정보는 `NutritionResolver`가 **조회**한다
- 사용자에게 보여줄 문장 생성

원칙은 하나다. **AI가 이해하고 판단한다. 코드가 계산하고 변경한다.**

자세한 경계 설계는 [`docs/architecture.md`](docs/architecture.md) 참고.

### 지금 되는 것 — 판단과 조회

**판단은 실측했다.** `jev-1.13.0`으로 골든셋 60건을 돌렸다 — intent **93~95%**, 섭취 판별 **96.7%**, reference **95%**. 확신도 임계값은 그 결과로 확정했고, reference는 **전략 A**(Jev가 고르고, 확신이 낮으면 코드 휴리스틱이 받는다)를 골랐다. 근거와 틀린 케이스 전부는 [`docs/architecture.md`](docs/architecture.md#31-jev-한국어-실측-phase-45)에 있다.

한 번의 판단은 **p50 261ms · 60건에 $0.0027**이다.

**칼로리 데이터가 들어왔다.** 식약처 식품영양성분DB(331,212행)에서 골라 `data/korean-foods.json`으로 번들했다. 앱은 런타임에 API를 호출하지 않는다.

```
갈비탕 한 그릇   → 362 kcal   (670g × 54 kcal/100g)
공기밥 한 공기   → 351 kcal   (210g × 167 kcal/100g)
라면 한 그릇     → 451 kcal   (550g × 82 kcal/100g)
삶은계란 두 개   → unmeasurable ← MFDS에 개당 무게가 없다
아메리카노 한 잔 → unmeasurable ← 잔 용량이 없다
커피 200ml      → 8 kcal       ← 양을 말해주면 바로 계산된다
마라탕          → unknown      ← 데이터셋에 아예 없다
```

`unmeasurable`과 `unknown`의 차이는 아래 "음식 커버리지"에서 설명한다. **모르는 건 모른다고 한다** — 데이터가 1인분 무게를 주지 않으면 그럴듯한 숫자를 만들지 않고 되묻는다.

### 지금 되는 것 — 기록 · 수정 · 삭제

```
나: 갈비탕 하나 먹었어
앱: 기록했어요. 오늘 362 kcal 먹었어요. 1,738 kcal 남았어요.

나: 밥 한 공기 먹었어
앱: 어떤 밥인가요?   [쌀밥] [현미밥]
나: (쌀밥 선택)
앱: 기록했어요. 오늘 713 kcal 먹었어요. 1,387 kcal 남았어요.

나: 커피 한잔 마셨어
앱: 아메리카노는 찾았어요. 얼마나 드셨는지 g이나 ml로 알려주세요.
나: 200ml
앱: 기록했어요. 오늘 721 kcal 먹었어요. 1,379 kcal 남았어요.

나: 마라탕 먹었어
앱: 마라탕은 아직 정보가 없어요.        ← 저장하지 않는다
```

```
나: 아까 밥 반만 먹었어
앱: 밥을 고칠까요?   [네] [아니요]
나: (네)
앱: 쌀밥을 고쳤어요. 오늘 537 kcal 먹었어요. 1,563 kcal 남았어요.

나: 밥 지워줘            ← 쌀밥과 김밥이 둘 다 있을 때
앱: 어떤 기록을 취소할까요?   [김밥 한 줄] [쌀밥 한 공기]
```

**삭제는 스스로 고르지 않는다.** 말이 두 기록에 걸리고 그 둘이 서로 다르면, 최근 것을 고르는 대신 되묻는다. 지운 뒤에는 눈치채기 어렵기 때문이다.

**되묻는 동안에는 아무것도 저장하지 않는다.** 한 문장이 두 음식을 말하면 둘 다 확정될 때까지 기다렸다가 기록 하나로 저장한다. 중간에 `취소`라고 하면 남는 것이 없다.

### 지금 안 되는 것

- **음식이 14개뿐이다.** 아래 "음식 커버리지" 참고 — 버그가 아니라 선택이다
- **정정 문법을 다 읽지는 못한다.** `아까 밥 반만 먹었어`는 되지만 `갈비탕 반 그릇만 먹었어`는 양을 읽지 못해 되묻는다. 문장 파서가 "먹었어" 쪽 문법에 맞춰져 있기 때문이다. 틀린 값을 저장하는 대신 묻는다
- **추천을 못 한다.** `저녁 뭐 먹지?`는 의도까지만 알아듣고 답하지 못한다
- 사진 입력, 단백질 등 macro, 로그인, 서버 DB 없음. 기록은 이 브라우저에만 남는다
- LLM fallback 파서는 자리만 있고 호출하는 코드가 없다

## 음식 커버리지 — 좁은 건 선택이다

데이터셋에 **14개**가 들어 있다. 적은 이유가 있다.

식약처 DB는 **331,212행**이고, 이름 검색은 부분 일치다. 그대로 검색해서 첫 결과를 쓰면 이런 일이 벌어진다.

| 검색 | 돌아오는 것 | 진짜 |
| --- | --- | --- |
| `커피` | 커피번 **389 kcal/100g** | — |
| `아메리카노` (정확 일치!) | 인스턴트 **분말** 200 kcal/100g | 내린 커피 **4 kcal/100g** |
| `바나나` (정확 일치!) | 바나나맛 **과자** 454 kcal/100g | 생바나나 ~80 |
| `갈비탕` | 품목대표만 **6행**, 27~89 kcal/100g | — |

**정확 일치조차 안전하지 않다.** 그래서 런타임에 331k행을 검색하지 않고, 사람이 행을 눈으로 확인한 `FOOD_CD`만 `seeds.ts`에 고정해 데이터셋을 만든다. 앱이 멀쩡히 돌면서 조용히 틀린 숫자를 저장하는 것이 이 프로젝트에서 가장 피해야 할 실패다.

그래서 두 가지 "없음"은 정상 동작이다.

| 상태 | 뜻 | 앱이 하는 말 |
| --- | --- | --- |
| `unknown` | 데이터셋에 그 음식이 없다 | "마라탕은 아직 정보가 없어요." 저장하지 않는다 |
| `unmeasurable` | 음식은 알지만 **그 단위의 무게 근거가 없다** | "아메리카노는 찾았어요. 얼마나 드셨는지 g이나 ml로 알려주세요." |

뒤쪽은 사용자가 `200ml`이라고 한 마디 하면 바로 풀린다. 억지로 1인분을 추정하지 않는다.

### 앞으로 늘리는 방법 — usage-driven

미리 수백 개를 채우지 않는다. **실제로 써 보면서 `unknown`이 반복되는 음식부터** 그 행을 확인하고 seed에 추가한다. 쓰지도 않을 음식을 손으로 검증하는 비용이 가장 아깝고, 검증 없이 넣으면 위 표의 함정을 밟는다.

### 한국어 골든셋

`fixtures/korean-inputs.json`에 추가 / 수정 / 삭제 / 질문 / 추천 / 비섭취 / 모호 7개 범주 **60건**이 들어 있다. 스키마는 `src/ai/judgment/goldenSet.ts`.

Jev는 영어가 주 훈련 언어이고 한국어를 포함한 CJK는 정확도가 낮을 수 있다고 공식 문서에 명시돼 있다. 그래서 모델 버전이나 질문 문구를 바꿀 때마다 이 골든셋으로 회귀 측정한 뒤 반영한다. 기대값은 *모델이 지금 내놓는 답*이 아니라 *맞는 답*이다. 실패하는 케이스는 고장난 fixture가 아니라 알려진 격차다.

## 배포 메모

브라우저 `localStorage`에만 저장하므로 **DB 없이 정적 호스팅 + 서버리스 함수만으로 돌아간다.**

- 런타임 환경변수는 `TYPESAFE_API_KEY` 하나, 그마저도 없으면 mock 판단으로 동작한다
- 영양 데이터는 `data/korean-foods.json`이 번들되므로 **런타임에 식약처 API를 호출하지 않는다**
- 서버 라우트는 `/api/chat`, `/api/resolve` 둘 다 stateless. 세션도 저장소도 없다
- `NEXT_PUBLIC_*` 변수 없음. secret은 서버에만 있다
- `pnpm sync:mfds` / `pnpm eval:jev`는 개발자용이며 빌드 중 실행되지 않는다

배포 전 확인할 것은 [`docs/HANDOFF.md`](docs/HANDOFF.md)의 체크리스트에 정리되어 있다.

## 이후 확장 아이디어

- 서버 DB + 인증 (repository 인터페이스만 교체)
- 데이터셋 항목 확대 (`seeds.ts`에 확인한 `FOOD_CD` 추가)
- 단백질 등 macro 표시 — 식약처 응답에 이미 들어 있다
- 자주 먹는 음식 빠른 재입력

의학적 진단이나 치료를 목적으로 하는 서비스가 아니다.
