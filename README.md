# 오늘 얼마 먹어도 돼?

먹은 걸 평소 말하듯 입력하면 기록하고, **오늘 앞으로 얼마나 더 먹을 수 있는지** 바로 보여주는 앱.

> **v0.2** — MVP를 며칠 실제로 써 본 뒤 막혔던 세 가지(음식 커버리지 · 사람 단위 · 목표 칼로리)를 고쳤습니다. 아래 대화는 실제 출력입니다.

```
나: 갈비탕 하나 먹었어
앱: 기록했어요. 오늘 362 kcal 먹었어요. 1,738 kcal 남았어요.

나: 밥 한 공기 먹었어
앱: 어떤 밥인가요?   [쌀밥] [현미밥]
나: (쌀밥)
앱: 기록했어요. 오늘 713 kcal 먹었어요. 1,387 kcal 남았어요.

나: 아까 갈비탕 반만 먹었어
앱: 갈비탕을 고쳤어요. 오늘 532 kcal 먹었어요. 1,568 kcal 남았어요.
```

## 핵심 UX

화면은 셋뿐이다. **오늘 상태 · 오늘 먹은 것 · 대화 입력창.**

커뮤니티, 배지, 스트릭, 체중 그래프, 운동 프로그램, 물 섭취 기록은 넣지 않는다. 사용자가 CRUD 폼을 직접 조작하는 대신 자연어로 말하면 앱이 의도를 판단해 기록을 바꾼다. 판단이 애매하면 멋대로 바꾸지 않고 **짧게 되묻는다.**

말투도 짧게 유지한다. 과한 격려나 건강 코칭을 하지 않는다.

```bash
pnpm install

pnpm typecheck
pnpm lint
pnpm test
pnpm build

pnpm eval:jev                  # 실제 Jev로 골든셋 60건 측정 (TYPESAFE_API_KEY 필요)
EVAL_JUDGE=mock pnpm eval:jev  # 규칙 기반 fallback 기준선 (키 불필요)
pnpm eval:food-coverage        # 음식 입력 말뭉치 191건을 파서로만 채점 (오프라인, 무료)
pnpm eval:food-judgment        # 같은 말뭉치를 production 경로(runChat)로, 후보 필터 off/on 비교 (Jev 호출, 약 $0.01)
pnpm sync:mfds                 # 식약처에서 데이터셋 재생성 (MFDS 키 필요)
MFDS_QUERY="순두부찌개" pnpm candidates:mfds   # 음식 추가 전 후보 행 보기 (고르지 않음)
```

`eval:*`·`sync:mfds`·`candidates:mfds`는 개발용이다. `pnpm test`는 네트워크를 전혀 타지 않는다. `eval:food-coverage` 결과는 `fixtures/food-input-coverage.baseline.json`에 고정돼 있어, 파서 동작이 바뀌면 `pnpm test`가 실패한다(의도한 변경이면 `FOOD_COVERAGE_UPDATE=1 pnpm eval:food-coverage`로 갱신).

pnpm이 없다면 corepack으로 켠다.

```bash
corepack enable --install-directory ~/.local/bin pnpm
```

## 환경변수

`.env.example`을 `.env.local`로 복사해서 쓴다. 실제 키는 절대 커밋하지 않는다.

변수는 **런타임에 필요한 것**과 **로컬 데이터 동기화에만 쓰는 것**으로 나뉜다. 아래는 코드의 실제 사용처를 추적해서 정리한 것이다.

### 런타임 (배포 시 설정)

| 변수 | 필수 | 사용처 |
| --- | --- | --- |
| `TYPESAFE_API_KEY` | **아니오** | `src/app/api/chat/route.ts` — Jev 판단. **없으면 결정론적 mock 판단으로 앱 전체가 정상 동작한다.** 없는 상태는 지원되는 상태지 고장이 아니다 |
| `FOOD_CANDIDATE_FILTER` | 아니오 (기본 `off`) | `on`이면 add마다 Jev 요청을 하나 더 병렬로 보내, 먹지 않은 구절("팀원들", "너무 매워")에 대한 질문을 뺀다. 기록된 음식은 건드리지 않고, 실패하면 필터 없이 전부 묻는다. 키가 없으면 켜도 동작하지 않는다 |
| `FOOD_CANDIDATE_TIMEOUT_MS` | 아니오 (기본 1500) | 위 요청의 timeout. 재시도는 없다 |

**키가 필요한 건 `TYPESAFE_API_KEY` 하나뿐이다.** 앱은 커밋된 `data/korean-foods.json`을 읽으므로 실행 중 외부 영양 API를 호출하지 않는다.

## Jev가 하는 일 / 하지 않는 일

Jev는 ChatGPT 같은 생성형 챗봇의 대체재가 아니다. **문장을 만들지 않고, 타입이 정해진 판단과 확률을 돌려준다.**

**하는 일**

- intent 판단 — `add_food` / `modify_food` / `delete_food` / `ask_status` / `ask_recommendation` / `other`
- 지금 말한 게 실제로 먹은 것인지 (`갈비탕 칼로리 높아?`를 기록으로 저장하면 안 된다)
- 기록을 바꾸기 전에 사용자 확인이 필요한지
- 최근 기록 중 무엇을 가리키는지 (`아까 밥`이 어느 항목인지)

**하지 않는 일**

- 산술 (`2100 - 1580`은 TypeScript가 한다)
- 칼로리 합산
- 음식의 칼로리 값 생성 — 영양정보는 `NutritionResolver`가 **조회**한다
- 사용자에게 보여줄 문장 생성

원칙은 하나다. **AI가 이해하고 판단한다. 코드가 계산하고 변경한다.**

자세한 경계 설계는 [`docs/architecture.md`](docs/architecture.md) 참고.

### 지금 되는 것 — 판단과 조회

**판단은 실측했다.** `jev-1.13.0`으로 골든셋 60건을 돌렸다 — intent **93~95%**, 섭취 판별 **96.7%**, reference **95%**. 확신도 임계값은 그 결과로 확정했고, reference는 **전략 A**(Jev가 고르고, 확신이 낮으면 코드 휴리스틱이 받는다)를 골랐다. 근거와 틀린 케이스 전부는 [`docs/architecture.md`](docs/architecture.md#31-jev-한국어-실측-phase-45)에 있다.

한 번의 판단은 **p50 261ms · 60건에 $0.0027**이다.

**칼로리 데이터가 들어왔다.** 식약처 식품영양성분DB(331,212행)에서 골라 `data/korean-foods.json`으로 번들했다. 앱은 런타임에 API를 호출하지 않는다.

```
갈비탕 한 그릇   → 362 kcal    (670g × 54 kcal/100g, 식약처 행의 1인분)
공기밥 한 공기   → 351 kcal    (210g × 167 kcal/100g)
삶은 달걀 두 개  → ~150 kcal   (2 × 50g ← 식품교환표 계량, × 150 kcal/100g ← 식약처)
바나나 1개       → ~77 kcal    (100g ← "바나나 50g = 중 1/2개")
두유 1팩         → ~124 kcal   (200mL ← 시판 180~200mL 범위에서 고른 상단값, typical)
닭가슴살 1팩     → unmeasurable ← 팩 무게는 제품마다 달라 공개 기준이 없다 → g 질문
고기만두 5개     → unmeasurable ← 인분으로만 발행된 음식을 "개"로 → 되묻는다
마라샹궈         → unknown     ← 데이터셋에 아예 없다
```

`~`는 추정이라는 뜻이고, 누르면(hover) 어떤 계량·출처를 썼는지 보인다. **모르는 건 모른다고 한다** — 근거가 있는 계량만 쓰고, 없으면 그럴듯한 숫자를 만들지 않고 되묻는다.

```
나: 갈비탕 하나 먹었어
앱: 기록했어요. 오늘 362 kcal 먹었어요. 1,738 kcal 남았어요.

앱: 닭가슴살은 찾았어요. 얼마나 드셨는지 g이나 ml로 알려주세요.

앱: 마라샹궈는 아직 정보가 없어요.        ← 저장하지 않는다
```

```
나: 아까 밥 반만 먹었어
앱: 밥을 고칠까요?   [네] [아니요]
나: (네)
앱: 쌀밥을 고쳤어요. 오늘 537 kcal 먹었어요. 1,563 kcal 남았어요.

나: 밥 지워줘            ← 쌀밥과 김밥이 둘 다 있을 때
앱: 어떤 기록을 취소할까요?   [김밥 한 줄] [쌀밥 한 공기]
```

**삭제는 스스로 고르지 않는다.** 말이 두 기록에 걸리고 그 둘이 서로 다르면, 최근 것을 고르는 대신 되묻는다. 지운 뒤에는 눈치채기 어렵기 때문이다.

**되묻는 동안에는 아무것도 저장하지 않는다.** 한 문장이 두 음식을 말하면 둘 다 확정될 때까지 기다렸다가 기록 하나로 저장한다. 중간에 `취소`라고 하면 남는 것이 없다.

**한 문장이 기록 하나를 고치면서 새 음식도 말하면**(떡볶이가 있을 때 "떡볶이랑 튀김 먹었는데 떡볶이는 반만") 둘 다 보여주고 확인받는다 — "떡볶이를 고치고 튀김을 새로 기록할까요?" 어느 쪽도 조용히 버리지 않는다.

### 지금 안 되는 것

- **음식은 426개다.** 흔한 한식·외식·분식·간식·카페 음료를 덮지만 유한하다 — `마라샹궈`·`포케`·`타코`·`크로플`·`소금빵`·술, 브랜드 제품은 `unknown`(식약처 DB에 특정 회사 제품 행만 있다). 마라탕·치킨·피자·케이크·아이스크림처럼 재료와 양에 따라 차이가 큰 음식은 식약처 행의 값으로 바로 기록하고 "칼로리 차이가 클 수 있어요"라고 알린다. 아래 "음식 커버리지" 참고
- **무게 근거가 없는 음식은 양을 묻는다.** 보쌈·목살·돼지갈비·차돌박이·견과류·감자칩처럼 1인분 무게를 말해 주는 행이 없는 음식은 "얼마나 드셨는지" 되묻는다. 칼로리를 묻는 것이 아니라 g을 묻는다
- **음식 앞뒤에 다른 말이 붙으면 못 읽을 때가 있다.** "회의 끝나고 밥", "아메리카노 한 잔 더"는 음식으로 읽지 못해 칼로리를 되묻는다. 틀린 값을 저장하는 대신 묻는다
- **같은 음식이 이미 기록된 날에는 판단이 흔들린다.** 김밥이 있는 날 "김밥 먹으려다가 그냥 굶었어"를 삭제로 읽을 수 있다(확인을 거치므로 조용히 지워지지는 않는다)
- **추천을 못 한다.** `저녁 뭐 먹지?`는 의도까지만 알아듣고 답하지 못한다
- 사진 입력, 단백질 등 macro, 로그인, 서버 DB 없음. 기록은 이 브라우저에만 남는다
- LLM fallback 파서는 자리만 있고 호출하는 코드가 없다

## 음식 커버리지

데이터셋에 **426개**가 들어 있다 (v0.1 14개 → v0.2 83개 → v0.3에서 다이어트 음식 추가 109개 → 2026-10-01 외식·반찬 11개 추가 120개 → 2026-10-02 v1 커버리지 확장 244개 → 같은 날 2차 확장 426개). 이 중 70개는 고편차(`variance: "high"`) 음식이다.

2차 확장은 음식 수보다 **평소에 그냥 하는 말**을 겨냥했다. `케이크`·`아이스크림`·`샌드위치`·`만두`·`주스`·`파스타`·`국밥`·`회`처럼 종류를 말하지 않은 이름은, 식약처에 일반 행이나 모듬 행이 있으면 그 행으로 바로 기록하고 편차를 알린다. 일반 이름을 특정 음식의 별칭으로 붙이지는 않는다 — `케이크`는 케이크 행이지 치즈케이크의 다른 이름이 아니다. 일반 행이 없고 종류별 값이 크게 갈리는 이름(`샐러드`, `튀김`, `떡`, `해장국`)은 여전히 되묻거나 `unknown`이다.

### 왜 14개에서 늘렸나

v0.1은 "잘못된 행을 고르느니 `unknown`"이라는 이유로 14개만 넣고, 실제로 쓰면서 반복되는 `unknown`부터 늘리기로 했다. 그 원칙은 맞았지만 실제로 써 보니 `unknown`이 너무 잦아서 **기록 도구로 쓸 수가 없었고, 쓰지 못하니 늘릴 근거도 쌓이지 않았다.** 그래서 다이어터가 매일 기록하는 범주를 먼저 채웠다. 정확성 원칙은 그대로다.

### 여전히 이름으로 고르지 않는다

식약처 DB는 **331,212행**이고, 이름 검색은 부분 일치다. 그대로 검색해서 첫 결과를 쓰면 이런 일이 벌어진다.

| 검색 | 돌아오는 것 | 진짜 |
| --- | --- | --- |
| `커피` | 커피번 **389 kcal/100g** | — |
| `아메리카노` (정확 일치!) | 인스턴트 **분말** 200 kcal/100g | 내린 커피 **4 kcal/100g** |
| `바나나` (정확 일치!) | 바나나맛 **과자** 454 kcal/100g | 생바나나 **77** (`R108-037000001-0000`) |
| `갈비탕` | 품목대표만 **6행**, 27~89 kcal/100g | — |

그래서 전부 사람이 행을 눈으로 확인한 `FOOD_CD`를 `seeds.ts`에 고정했다. 런타임에 MFDS를 검색해 사용자에게 고르게 하는 방식은 쓰지 않는다 — `바나나` 1,835행을 보여줄 수 없고, 이름이 같아도 과자다.

| 상태 | 뜻 | 앱이 하는 말 |
| --- | --- | --- |
| `unknown` | 데이터셋에 그 음식이 없다 | "마라샹궈는 아직 정보가 없어요." 저장하지 않는다 |
| `unmeasurable` | 음식은 알지만 **그 단위의 무게 근거가 없다** | "닭가슴살은 찾았어요. 얼마나 드셨는지 g이나 ml로 알려주세요." |

### 사람 단위 — serving reference

식약처는 100g당 에너지를 주지만 **달걀 1개의 무게는 주지 않는다.** 그래서 v0.1은 `삶은 달걀 두 개`에 "몇 g인가요?"라고 물었다. 달걀을 저울에 올리는 사람은 없다.

v0.2는 "사람 단위 → g" 변환을 별도 파일(`servingReferences.ts`)로 분리했다. 여기에는 **칼로리가 하나도 없고**, 출처에 **인쇄된** 가정용 계량만 들어간다.

| 우선순위 | 출처 | 표시 |
| --- | --- | --- |
| 1 | 식약처 행 자체의 1인분 (`갈비탕 1그릇 = 670g`) | 그대로 |
| 2 | 제조사 표시량 (식약처 가공식품 행) | 그대로 |
| 3 | 공공·전문 표준의 가정용 계량 — 대한당뇨병학회 식품교환표(2010) 등 | `~` + 출처 |
| 4 | 실데이터에서 온 전형 크기 — 카페 음료 355mL (식약처 카페 음료 행) | `~` + 출처 |
| 5 | 사용자가 말한 g·ml | 언제나 가능 |

근거를 찾지 못한 것(`닭가슴살 1팩`, `요거트 1개`, `삼각김밥 1개`, `계란후라이 1개`, `콜라 1캔`, `귤·참외·복숭아 1개`)은 억지로 채우지 않고 g을 묻는다 — 포장에 무게가 인쇄되어 있어 오히려 정확하다. 전체 목록과 출처는 [`docs/architecture.md` §4.3](docs/architecture.md).

### 음식 추가하기

```
1. MFDS_QUERY="순두부찌개" pnpm candidates:mfds   ← 후보 행을 본다 (도구는 고르지 않는다)
2. 행을 읽고 FOOD_CD를 seeds.ts에 적는다
3. 원재료라 "1개"가 필요하면, 출처에 인쇄된 계량이 있을 때만 servingReferences.ts에
4. pnpm sync:mfds && pnpm test
```

### 한국어 골든셋

`fixtures/korean-inputs.json`에 추가 / 수정 / 삭제 / 질문 / 추천 / 비섭취 / 모호 7개 범주 **60건**이 들어 있다. 스키마는 `src/ai/judgment/goldenSet.ts`.

Jev는 영어가 주 훈련 언어이고 한국어를 포함한 CJK는 정확도가 낮을 수 있다고 공식 문서에 명시돼 있다. 그래서 모델 버전이나 질문 문구를 바꿀 때마다 이 골든셋으로 회귀 측정한 뒤 반영한다. 기대값은 *모델이 지금 내놓는 답*이 아니라 *맞는 답*이다. 실패하는 케이스는 고장난 fixture가 아니라 알려진 격차다.

## 배포 메모

브라우저 `localStorage`에만 저장하므로 **DB 없이 정적 호스팅 + 서버리스 함수만으로 돌아간다.**

- 런타임 환경변수는 `TYPESAFE_API_KEY` 하나, 그마저도 없으면 mock 판단으로 동작한다
- 영양 데이터는 `data/korean-foods.json`이 번들되므로 **런타임에 식약처 API를 호출하지 않는다**
- 서버 라우트는 `/api/chat`, `/api/resolve` 둘 다 stateless. 세션도 저장소도 없다
- `NEXT_PUBLIC_*` 변수 없음. secret은 서버에만 있다
- `pnpm sync:mfds` / `pnpm eval:jev`는 개발자용이며 빌드 중 실행되지 않는다

배포 전 확인할 것은 [`docs/HANDOFF.md`](docs/HANDOFF.md)의 체크리스트에 정리되어 있다.

## 목표 칼로리 계산기 (v0.2)

첫 방문에 "하루 목표를 대략 계산해 볼까요?"를 한 번 묻는다. [계산하기] / [직접 입력할게요] — 어느 쪽을 골라도 다시 자동으로 뜨지 않고, 계산기는 목표 영역의 "계산해서 정하기"로 언제든 연다. 이미 목표가 있는 사용자에게는 뜨지 않는다.

```
BMR (Mifflin-St Jeor) × 활동 계수(1.2 / 1.375 / 1.55 / 1.725) = 예상 유지 칼로리
유지 = 유지 칼로리 · 천천히 감량 = −300 · 빠르게 감량 = −700
```

- 화면은 "**예상** 유지 칼로리 약 N kcal"이라고만 말한다. 측정값이 아니다
- **자동 제안 하한**(여 1,200 / 남 1,600 kcal) — 앱이 스스로 제안하는 감량 목표에만 거는 보수적인 guardrail이다(NHLBI 저열량식 범위의 상단). 안전·위험 기준이 아니다. 그 아래 모드는 "앱이 자동으로 제안하지 않는 범위예요"로 보이고, 유지 모드와 수동 입력은 막지 않는다
- 기술적 입력 경계(`MIN_DAILY_GOAL_CALORIES` 500)도 건강 기준이 아니며, 위 guardrail과 별개다
- 계산 결과는 평범한 `DailyGoal`이 된다. **마지막에 정한 것이 이긴다** — 직접 입력이 언제든 덮어쓴다

> **입력한 정보는 이 기기에만 저장되며 서버에 전송되지 않습니다. 다른 기기와 자동으로 공유되지 않습니다.**

이 문장은 테스트로 지킨다(`src/privacy.test.ts`): `/api/chat` 본문은 필드 4개뿐이고, 두 API route에서 import 그래프를 따라가도 프로필 모듈에 닿지 않으며, analytics 의존성이 없다. 공식·계수·자동 제안 하한의 근거는 [`docs/architecture.md` §4.3](docs/architecture.md).
